1. PROJECT SUMMARY

Objective:
Build and release the 20-feature NoteForge daily-driver program while preserving local-first ownership, lossless Markdown round-tripping, existing user data, offline operation, accessibility, and the canonical System by Dave deployment.

Key Outcomes:
- Ship all 20 planned capabilities: local revision history, rename-safe wikilinks, saved searches, idempotent Daily notes, Quick Capture, heading outline, find/replace, Archive, contextual backlinks, unlinked mentions, task dashboard, note properties, calendar, web clipper, back/forward/recents, tabs and split view, bulk note actions, backup center, folder import/reconciliation, and block links/transclusion.
- Preserve every existing schema-version-3 vault through tested forward migrations while retaining the IndexedDB identifier `my-notes-app`, all note IDs, Markdown content, images, tags, banners, nesting, Trash state, settings, and migration behavior.
- Keep Markdown as the source of truth: every new content syntax must pass parse/serialize fixed-point tests, and every new metadata field must survive JSON backup/export/import without loss.
- Keep every release green through `npm test`, `npm run test:browser`, `npm run build`, and `npm audit --audit-level=high`, with zero unexpected page, console, request, or HTTP errors in the browser runner.
- Publish each completed release to the GitHub Pages mirror and the canonical `https://systembydave.com/noteforge/` route, with exact source provenance, canonical/mirror bundle parity, service-worker update proof, and disposable-profile interaction checks.

Assumptions:
- The phrase “based on the most recent user request” means this plan must implement the 20 features from the immediately preceding NoteForge brainstorm, not merely select one feature. The features are grouped into independently releasable phases to keep the program reviewable.
- No delivery deadline, budget, or team size was supplied. Timelines assume one senior JavaScript developer working primarily on NoteForge, with part-time UX/accessibility review and release verification; elapsed time increases if only one person performs every review.
- NoteForge remains a local-first static PWA with no mandatory account, server, cloud sync, collaboration system, telemetry, or remote database. Cloud sync and inline-WYSIWYG/editor-framework adoption remain excluded architectural forks.
- Existing product behavior and visual language are authoritative where no mockup was supplied. New UI uses the current component, modal, command-palette, tokenized CSS, mobile breakpoint, keyboard, focus-management, and reduced-motion conventions.
- Schema changes are permitted for these new features, but they must be additive, sequential migrations from the existing schema-version-3 payload. The value and meaning of schema version 3 and the IndexedDB identifier `my-notes-app` must not be altered.
- Node.js 22 remains the supported local and CI baseline. Existing dependency major versions remain fixed unless a separate reviewed decision authorizes a major upgrade. The `yaml` package may be added for standards-compliant frontmatter parsing only after license, bundle-size, CSP, and `npm audit` checks pass; it must be lockfile-pinned and isolated behind a small adapter.
- Quick Capture supports text, URL, clipboard, and local image capture inside the app. The static PWA share target uses a GET action for title/text/URL on supporting platforms; shared binary files fall back to the in-app image picker because GitHub Pages cannot accept a POST upload endpoint.
- Web clipping ships first as a local bookmarklet plus a NoteForge capture route. A separately distributed browser extension is not required for acceptance and would need its own store-signing and review plan.
- Folder reconciliation is manual and user-initiated. It reads a selected directory, previews additions/changes/conflicts, and applies only confirmed operations; it is not background or two-way cloud sync.
- “Lock” or encryption features, print/PDF export, and a spatial canvas are not part of this 20-feature scope because they were not included in the final prioritized list. They remain candidates for a later program.
- GitHub authentication, Pages permissions, and both existing repository remotes remain available to the release owner. Missing access changes release readiness to Blocked but does not change implementation scope.

Phase Name: Phase 1: Revision History and Backup Center

Goal:
Add recovery from accidental edits and visible storage/backup health before new metadata and high-volume workflow features increase migration risk.

Key Milestones:
- Extend `src/core/storage.js` with namespaced key enumeration and batched reads/writes without changing `DB_NAME`, `STORE`, or existing note/config keys; add fallback behavior that reports revision-history unavailability when durable IndexedDB is unavailable.
- Add `src/core/revision-store.js` with revision records containing note ID, timestamp, content hash, metadata hash, reason, and parent revision; store identical content once by SHA-256 and enforce configurable per-note count and age retention limits.
- Capture revisions only at durable boundaries—after a completed autosave, before import/reconciliation, before destructive bulk replacement, and before restoring another revision—rather than on every keystroke.
- Add `src/components/history-view.js` with chronological preview, text diff, Restore, and Restore as Copy actions; restoration must create a safety revision first and must never silently overwrite the current note.
- Add `src/components/backup-view.js` showing IndexedDB/fallback status, storage usage/quota when available, last successful persistence, last portable backup, rolling local vault snapshots, Download JSON Backup, Verify Backup, and Restore Preview.
- Add retention, hash-deduplication, restore, quota-error, fallback-storage, malformed-backup, keyboard, focus-trap, mobile, and large-image regression coverage; update README and ROADMAP when the phase ships.

Dependencies:
- Phase 0 baseline, fixtures, revision-retention decision, and release checklist completed.

Required Resources:
- NoteForge maintainer.
- Browser IndexedDB, Web Crypto SHA-256, StorageManager quota API where available, existing JSON import/export utilities, and Playwright.

Estimated Timeline:
2–3 weeks.

Senior JavaScript developer, with accessibility review by the designated QA reviewer.

Risks / Failure Points:

3. EXECUTION NOTES

Critical Sequencing Constraints:
- Complete Phase 0 before editing storage or schemas; later migrations require trusted schema-version-3 fixtures, explicit syntax contracts, and measured baselines.
- Ship revision history and backup recovery before rename rewrites, bulk replacement, frontmatter migration, or folder reconciliation; each of those operations needs a tested recovery point.
- Complete canonical title/alias resolution before contextual backlinks, unlinked mentions, properties aliases, block links, and folder identity matching; otherwise each later feature would encode a different resolution rule.
- Stabilize Archive and saved-query semantics before task and calendar aggregation so every derived view applies the same live/archived/trashed filters.
- Stabilize `@due()` and date behavior before property/calendar integration; changing task syntax after indexes and frontmatter filters ship would require avoidable migration work.
- Complete frontmatter and stable block IDs before folder reconciliation; external Markdown needs durable IDs to distinguish an update from an unrelated same-title file.
- Complete navigation history before tabs/split view; pane navigation must reuse one canonical history model rather than create parallel implementations.
- Do not merge a phase to `main` until its vertical slice, migrations, tests, docs, accessibility checks, and rollback path pass. Commit and push focused branches during work; merge only reviewed, releasable slices.
- Do not synchronize System by Dave until the reviewed NoteForge commit is built under Node 22 and its exact-SHA mirror deployment is green.

Parallelizable Work:
- During Phase 0, fixture creation, UX wireframes, architecture decisions, performance-corpus generation, and release-checklist drafting can proceed concurrently because they touch separate artifacts.
- In Phase 1, history-view UI can be built against a mock revision-store contract while the storage/revision implementation and pure retention tests proceed separately.
- In Phase 2, heading outline/navigation history can proceed in parallel with alias/link-rewrite internals after the resolution contract is frozen.
- In Phase 3, saved-search UI and current-note find/replace can proceed in parallel; Archive and bulk actions should share one developer because both modify note-list filtering and selection.
- In Phase 4, Quick Capture/PWA manifest work can proceed in parallel with pure task/date parsing; task dashboard must wait for the parser contract, while calendar UI can use fixture data.
- In Phase 5, properties UI can proceed against a mock frontmatter adapter while block-ID parsing/transclusion tests proceed separately; integration waits for both parsers to stabilize.
- In Phase 6, bookmarklet/capture-route work can proceed in parallel with folder diff planning; tabs/split-view work should remain isolated because it touches App, Editor, persistence, and most browser tests.
- Documentation, accessibility test cases, and adversarial fixtures should be updated continuously within every phase rather than deferred entirely to Phase 7.
